# RoboRAG：标准 MCP + CaP 最小闭环

分支：`feat/mhs-cap-minimal`。2026-10-23。
从基线 `79cbc94` 独立开发，保留主工作区的未提交工作。

## 第一阶段的核心

把 RoboDojo 的观测、控制和执行反馈统一接入标准 MCP，让一个大模型编写程序调用本体技能，
再根据实际反馈继续或修正。MCP 作为公开协议，不另造 MHS 版本或固定的机器人通用五接口。

大脑负责生成程序和判断下一步；小脑负责本体的插值、IK、执行与检查。
协议统一不等于不同机器人必须有相同动作：能力、参数和物理语义由各设备服务声明。
当前原生适配器是双 ARX-X5，CaP 核心不绑定它的工具名称。

## 实现与验收

- [x] 独立分支/工作区，保留 RAG 基线。
- [x] 标准 MCP client：能力协商、分页发现、schema 校验、工具/资源调用和标准结果。
- [x] 原生 RoboDojo MCP server：本体状态、RGB、末端位姿、关节目标、夹爪和执行回执。
- [x] 设备参考、当前状态、执行状态作为 MCP resources。
- [x] MCP / Isaac 分进程，复用原生控制器和任务终止条件，仿真 API 留在所属线程。
- [x] CaP 有界 Python 子集，局部条件/循环与连续工具调用。
- [x] 单模型 harness：程序 → 执行反馈 → 继续/修正；保留工作记忆与日志。
- [x] 不依赖五个固定接口；用另一个工具目录验证相同 CaP 核心。
- [x] 合成拒绝后的恢复；原生仿真通过 MCP 的状态/RGB/运动/停止烟测。
- [ ] 大模型 + RGB 完成一个原生短任务，并用外部原生评测确认结果。
- [ ] 冻结可复现案例，记录模型/技能版本、失败、成本和任务成绩。

原生接口烟测的脚本模型、合成夹持逻辑、CLI 替身测试都不能当作 Astra/Sol manipulation 成绩。
详见 [实现与运行](cap-mcp-minimal.md)。

## 后续研究的顺序

1. **先完成基础闭环**：确认大模型能通过标准 MCP 使用本体技能，证据可回放。
2. **明确记忆的对象**：程序片段、技能使用条件、失败原因和可观察的执行证据。
3. **比较检索时机**：规划前、失败后、模型主动请求；不默认每个控制步都 RAG。
4. **维护经验库**：来源、适用能力/技能版本、去重、证据验证及淘汰。
5. **扩展本体**：增加另一个设备的 MCP 适配器，测试 CaP 与经验的可迁移边界。

双模型监督、复杂 guidance 图、通用运动词表和完整异步作业系统不作为第一阶段前置条件。
