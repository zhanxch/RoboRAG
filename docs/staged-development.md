## 三种缓存与复用不能混算

模型的 cached input 是模型用量报告中的输入子集；阶段查询缓存是 `StageLibrary` 对相同语义请求的结果复用；阶段上下文复用是进入阶段时直接使用此前准备好的 guidance 与经验，可能完全不再调用检索。三个开发回合的查询缓存命中均为 0，但 fold/push/pour 上下文复用分别为 4、1、5。这些计数不能相加为“模型缓存命中次数”，也不能直接换算为美元节省。

输出已经包含 reasoning，不应再加一次。实际账单和模型 API 请求次数未知；每回合一个 `turn.completed` 是原生 CLI 的聚合用量记录，不等于只调用一次模型。动作段、阶段工具或参考展开次数也不是 API 请求次数。

## 倒球开发中的阶段切换缺口

初版倒球虽然原生成功，详细日志仍发现一次语义阶段越界：`agent-events.jsonl` 的 item 58 对抓取阶段的评估引用了进入抓取前的测量，被证据时效检查拒绝；item 59 进入对齐阶段因依赖未完成被拒绝。模型随后仍提交 item 60 的运输动作（`action-00013`，188→212 步），因此记录正确地将它归到仍生效的抓取阶段。item 61 修正评估并成功，item 62 才成功进入对齐阶段。不能将这次运输描述为已获准的对齐操作，也不能用最终成功掩盖它。

初版结构核验能确认每个动作有准确的当时阶段和回执，但不能证明模型在阶段切换失败后正确处理了意图。修复将对被拒绝的跨阶段切换增加持久派发限制：只有成功完成切换，或依据当前观测明确恢复原阶段，才能继续动作。观察、评估与获取上下文保持可用，不需要为普通恢复重新规划。

[追加开发登记](../experiments/staged_v1/transition-repair.json)在新试跑前记录此问题、修复边界和 standard layout 1 的单回合预算。它属于原协议允许的开发范围；正式四例回归场景未用于这次修复。修复后的版本须另行验证，不能继承初版 3/3 的效果声明。

## 实际失败请求与后续修复边界

两个原生成功回合均发生过一次 `prepare_stage` 参数失败，原始失败保留在各自 `agent-events.jsonl` 和 `mcp-server.log`：

- fold 实际提交 `arm="both"`，用于预览双手下摆折叠，收到 `arm must be left, right or empty`。随后省略 arm 的请求成功返回。
- push 实际提交 `arm="left next, right currently in contact"`，把当前接触手臂和后续换臂说明写进了过滤字段，收到同样的错误；它不是一次 `arm="both"` 请求。后续请求使用合法字段后继续执行。

评估报告的 `stage_searches` 4/7 是成功返回的阶段检索记录；上述各一次失败请求没有写入成功 `stage_prepared` ledger 或成功 MCP 审计行。原生 agent 事件显示每例显式 `prepare_stage` 各尝试 4 次，其中 3 次成功、1 次失败。旧实现先增加 cache miss 计数再触发参数校验，所以最后返回的累计 `cache_misses` 是 5/8，而成功完成检索是 4/7。这个差异来自失败尝试，不是隐藏的成功检索，也不能忽略失败请求的模型成本；终局 token 和墙钟已经包含这些尝试。

该接口修复已保存为 `85319e7fe5169305c91e14d5e1c29dbfa4451b8d`：MCP 的 arm 字段明确为 `""`、`"left"`、`"right"`、`"both"` 四个枚举；双手查询在库内映射为不限定单臂的过滤，无法解释的字符串在 miss 计数前拒绝。枚举让模型看见允许值，把换臂说明留在 observation/goal 中，减少接口含义歧义。[修复预检报告](../results/staged-arm-query-preflight-20261027.json)记录 135 项测试通过、零跳过，以及 ruff 和 diff 检查通过。

这个修复不属于 `43f8941` 的已测行为，三个原生成功回合都不能归因于它。预检报告明确记录该候选的原生验证尚待完成；本记录没有证据证明修复已提高恢复能力、成功率或成本。后续版本必须独立冻结、记录和验证，不能继承本轮分数。
