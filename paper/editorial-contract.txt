Research question: how can interaction experience organized as temporal dynamic graphs be built, retrieved, adapted into plans for unseen tasks, and followed by a hierarchy of agents and local execution?
Novelty candidate (needs literature comparison and empirical support): use a common, evidence-grounded interaction graph schema to connect offline annotation, graph retrieval, task-conditioned adaptation, and feedback-driven execution/repair. Merely using a graph, a long/short memory split, two models, or MCP is not an algorithmic novelty claim.

Core method part I: an annotation pipeline segments recorded interactions into phases; defines node and edge semantics; associates action, observation, actual feedback, conditions, provenance and uncertainty; forms temporal dynamic experience graphs; produces machine-checkable structured records plus compact agent-readable descriptions; indexes graphs and subgraphs, not just isolated text chunks.
Core method part II: GPT drafts a schema-conforming graph plan for an unseen task with grounded role variables; retrieves similar graphs/subgraphs from seen episodes; aligns roles, topology, phases, feedback and capability constraints; edits and validates a current plan; follows it using a high-level planner, a lower-cost supervisor, and a deterministic/local execution layer. Astra need not attend every action. Planning and observed completion must remain distinct.

Provisional common notation: goal g; observation o_t; visible history h_t; backend capability description c; source episode tau; versioned graph bank B; experience graph G; current plan P_t; actual execution history graph X_t. G, P and X share a node/edge schema but record historical evidence, prospective intent and current observed events respectively. D can refine schema; C and E must coordinate refinements.
Node: an interaction-phase instance, not an object. Fields: phase/skill role, object-role bindings, observed time span or planned symbolic interval, preconditions, intended effect, action/skill reference, evidence/feedback, provenance, confidence/status. Object relations live in predicates/attributes, not silently as a second incompatible graph.
Edges: precedence/temporal order; conditional transition; dependency; recovery link. Define semantics and distinguish observed order from causal proof. Actual repeated attempts are separate event nodes; a plan template may express retry logic, while execution unrolls attempts with a finite budget. Resource constraints govern any parallel branches. Current observed completion always uses available evidence, never the model's stated intent.
Dynamic: explicit updates at annotation boundaries, plan revision and completed execution events, with versions and stable identities; specify what is recomputed. No hidden oracle stage labels at deployment. Uncertain conditions can require new observation.
Bank lifecycle: freeze training graph bank for main held-out evaluation; current episode log updates separately. Test logs do not leak into the same main evaluation. Cross-episode accumulation is a separate chronological protocol with versioned banks.
Retrieval/adaptation: search whole graphs and phase-centered subgraphs; filter capability incompatibility; align semantic object roles and current conditions; adapt parameters and topology rather than replay source absolute trajectories; ground geometry from current observations and backend capabilities. Low-score or no compatible retrieval falls back to schema-conforming planning with explicit uncertainty.
System: compare backend-specific native access, common semantic wrapper with direct calls, and same semantic wrapper via MCP. This isolates effects of normalization from the wire protocol. Backends: RoboDojo, LIBERO, real robot as proposed scope; don't imply implemented coverage. Transport uniformity does not imply identical physics, skills or safety. Native controllers retain servo loops. Tests include interface reuse/porting effort, behavioral conformance, RPC overhead, compatibility failure handling, and task performance per backend.

Experimental design must test: graph construction quality; unseen task splits and graph compositional generalization; graph vs matched linearized evidence and sequence plans; retrieval vs no retrieval and state-only retrieval; adaptation vs raw reuse; hierarchical following vs high-level model-only on same controller; controlled failures/recovery; frozen-bank vs separate accumulation; platform protocol vs algorithm effects. Report success, task progress, evidence-grounded plan completion, recovery and cost with controlled data, observations, models and context budgets. No fake data or expected numeric gains.
Prior results: docs/results.md old dual-memory pilot, no consistent retrieval advantage. docs/roboicl-evaluation.md external matched-layout comparison, not graph method verification. docs/control-todo.md and docs/queued-control.md describe partial execution infrastructure, not completed hierarchical graph or MCP system. Distinguish completed native outcomes, interruption and unstarted runs. Use a compact status section, avoid repeating disclaimers throughout prose.
